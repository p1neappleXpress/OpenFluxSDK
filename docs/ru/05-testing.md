# Тестирование

*[Read in English](../05-testing.md)*

`scripttest` (`transport/script/cmd/scripttest` в основном репозитории) —
это инструмент, которым реально проверялся каждый из выпущенных
транспортов — обвязка для ручного смоук-теста на живой сети, а не мок. Нет
замены тестированию против настоящей цели: каждый транспорт, выпущенный
таким образом, был проверен против продуктивной инфраструктуры, а не
заглушки сервера.

## Базовое использование

```bash
go run ./transport/script/cmd/scripttest \
  -script transport/script/js/my-transport.js \
  -pubkey <hex pubkey> \
  -url "https://example.com/room/abc123" \
  -duration 30s \
  -send "hello"
```

Печатает каждый переход `setState`/`raise` и каждый полученный пакет
(обрезанный), затем строку статуса каждые 2 секунды:

```
[12:00:03.501] connected=true  state=connected    err="" sent=27B recv=115B reconnects=0
```

На что обращать внимание:

- **`connected` мигает** — обычно вызов `setState` в неправильном месте,
  либо цикл переподключения слишком агрессивен относительно собственных
  лимитов скорости настоящей цели.
- **`reconnects` растёт, а `recv` не двигается** — вы успешно
  переподключаетесь, но никогда реально ничего не получаете; проверьте
  свой regex/JSON-путь разбора сообщений на соответствие тому, что
  настоящая цель реально отправляет (залогируйте сырое сообщение вручную,
  прежде чем считать, что ваш парсер верен).
- **Стена капчи/логина** (`EVENT captchaRequired ...` или похоже) — см.
  поток инъекции куки ниже.

## Передача внешне решённых куки

Если у вашей цели есть стена капчи/логина, которую ваш скрипт правильно
обнаруживает, но не может решить внутри канала (это ожидаемо и нормально —
*обнаружение* — работа скрипта; решение вне канала, например через
телефон/WebView, — работа хост-приложения), `scripttest` может применить
за вас настоящий cookie jar:

```bash
go run ./transport/script/cmd/scripttest \
  -script transport/script/js/my-transport.js -pubkey <hex> \
  -url "https://example.com/doc/abc" \
  -cookies-file cookies.json -duration 20s
```

```json
{
  "https://example.com/doc/abc": {
    "session": "...",
    "auth_token": "..."
  }
}
```

Это вызывает `ApplyCookies` сразу после `Start()` — тот же путь, который
настоящее хост-приложение использует, чтобы передать куки решённой капчи в
уже работающий транспорт. Если ваш транспорт объявляет
`scopeCookiesToParentDomain: true` в `info()`, дважды проверьте, что кука
реально доходит до каждого поддомена, с которым вы работаете (см.
[06-lessons-learned.md](06-lessons-learned.md) про реальный баг, который
поймал именно этот сценарий).

**Никогда не коммитьте файл куки с реальными данными сессии.** Относитесь
к нему как к любому другому секрету.

## Нагрузочное тестирование

```bash
go run ./transport/script/cmd/scripttest \
  -script transport/script/js/my-transport.js -pubkey <hex> \
  -url "..." -duration 30s \
  -burst 5000 -burst-size 512
```

После подключения отправляет `-burst` пакетов размером `-burst-size` байт
подряд, максимально быстро, как быстро их принимает `Send()`, затем
сообщает прошедшее время и пропускную способность.

**Выбирайте количество burst-пакетов заметно больше 1024** (размер буфера
очереди записи — `transport.DefaultConfig().MaxQueueSize`). Ниже этого вы
измеряете только скорость заполнения буфера, а не реальную устойчивую
скорость транспорта — первые ~1024 пакета почти мгновенно ставятся в очередь
независимо от реальной скорости на проводе. Несколько тысяч пакетов делают
время заполнения буфера незначительной долей общего времени, так что
отображаемая пропускная способность сходится к реальной, ограниченной
write()-вызовами устойчивой скорости.

Числа, реально измеренные так на выпущенных транспортах: транспорт синхронизации
курсора документа с фреймингом Socket.IO (`mailru.js`) держал
~11 800 пакетов/с / 5,9 МБ/с на стороне отправки; транспорт pub/sub на
Centrifugo (`cupsonline.js`) с двумя реальными одновременными пирами
обменивался ~4 000 пакетов/с / 1,5 МБ/с *в каждую сторону* через настоящую
комнату. Используйте это как приблизительное ощущение того, что «разумно»
для сравнимой формы протокола, а не как цель, которую нужно достичь.

## Тестирование с двумя пирами

Некоторые транспорты имеет смысл тестировать только против *другого
экземпляра самого себя* (всё, что фундаментально работает peer-to-peer
через relay, а не клиент к фиксированному серверу). Запустите два процесса
`scripttest` против одной комнаты/URL одновременно:

```bash
go run ./transport/script/cmd/scripttest -script t.js -pubkey $K -url "$ROOM" -duration 25s -send "from-A" &
go run ./transport/script/cmd/scripttest -script t.js -pubkey $K -url "$ROOM" -duration 25s -send "from-B" &
wait
```

Затем проверьте строки `RECV` каждой стороны на наличие сообщения другой
стороны. Если ваша цель автоматически создаёт комнату/сессию при первом
посещении (многие backend-инструменты для совместной работы так делают —
проверьте, просто открыв базовый URL в браузере, прежде чем считать, что
нужен отдельный вызов API «создать комнату»), никакой особой настройки
кроме свежего URL/ID не требуется.

## Чтение `LastState()`/событий, когда что-то тихо ломается

Если запуск просто зависает в `reconnecting` с `err=""` и без строк
`EVENT`, ваш скрипт очень вероятно бросает исключение внутри callback'а,
результат которого никуда не пропагируется (обработчик `onmessage`
WebSocket, `.then` promise без `.catch`). goja/обёртка event loop молчаливо
глушат исключения внутри таких callback'ов намеренно (одно плохое сообщение
не должно убивать весь цикл чтения) — а это значит, что **вам** нужны
явные `try`/`catch` + `console.log`/`raise("debug", {...})` вокруг всего, в
безошибочности чего вы не на 100% уверены, иначе сбои там невидимы снаружи.
Это самая частая причина «почему ничего не происходит»; добавляйте
логирование прежде, чем считать, что сломан сам host API.

## Перед тем как выпускать

- Восстанавливается ли транспорт чисто после естественного сетевого сбоя
  (отключите wifi на 5 секунд), или он застревает?
- Не срабатывает ли лимит скорости/капча настоящей цели из-за слишком
  агрессивного цикла переподключения? (Экспоненциальный backoff с джиттером,
  с ограничением сверху, — паттерн, который использует каждый выпущенный
  транспорт; копируйте `reconnectBackoff` одного из них, а не изобретайте
  новую кривую.)
- Запустили ли вы хотя бы один burst/нагрузочный тест, даже маленький?
  Транспорт, работающий только на hello-world скоростях пакетов, удивит вас
  в продакшене.
