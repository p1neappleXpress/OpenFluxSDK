# Подпись и упаковка

*[Read in English](../04-signing-and-packaging.md)*

Подпись — это **вся** граница безопасности для скриптового транспорта: нет
никакой другой проверки доверия и никакого ограничения возможностей внутри
рантайма. Разберитесь с этой моделью, прежде чем выпускать что-либо: скрипт,
подписанный ключом, которому вы доверяете, может делать *что угодно*, что
позволяет host API (подключаться куда угодно, запрашивать что угодно,
открывать произвольные сокеты). Это осознанное решение — см.
[01-overview.md](01-overview.md) — но это значит, что управление ключами —
это вся игра.

## Простой `.js` + `.sig`

Самая простая форма: файл `<name>.js` и отдельная подпись `<name>.js.sig`
(байты ed25519-подписи в чистом виде) рядом с ним.

```bash
go run ./transport/script/cmd/scriptsign genkey priv.key pub.key
go run ./transport/script/cmd/scriptsign sign priv.key transport/script/js/my-transport.js
go run ./transport/script/cmd/scriptsign verify pub.key transport/script/js/my-transport.js
```

`genkey` записывает оба ключа в hex, одной строкой, без заголовков —
`priv.key` с правами `0600`. **Никогда не коммитьте приватный ключ в git.**
Каждый продуктивный ключ собственных транспортов основного репозитория
живёт полностью за пределами репозитория (путь вида `~/oflx-keys/`, права
600).

При загрузке рантайм читает `<name>.js`, читает `<name>.js.sig` и вызывает
`ed25519.Verify(pubKey, scriptBytes, sig)` — отказ закрытый, никакого
частичного доверия, никакого «предупредить и продолжить».

## Пакеты `.flux`

Файл `.flux` — это zip-архив, содержащий:

- `manifest.json` — `{name, version, author, description, icon}` (`icon`
  указывает на другой файл внутри того же архива, например `"icon.png"`)
- `main.js` — сам скрипт (уже собранный — см. ниже — если он использует
  локальные `require()`)
- опциональный файл иконки
- `package.sig` — подпись

**Подпись покрывает весь манифест вместе со скриптом и иконкой**
(конкатенация с указанием длины, чтобы не было неоднозначности из-за
отсутствующей/пустой иконки) — не только `main.js`. Это значит, что
`name`/`author`/`description`/`icon` легитимно подписанного пакета нельзя
подменить без вашего приватного ключа — иначе подпись становится
недействительной. Если вы хотите подписывать только скрипт и считать
метаданные неавторизованными (чисто косметическими, для UI-списка) — это
архитектурное решение, которое можно принять, просто не используя `.flux`
вообще и поставляя обычные `.js`+`.sig` — внутри самого `.flux` промежуточного
варианта «частичной подписи» не существует.

```bash
go run ./transport/script/cmd/scriptsign pack \
  priv.key manifest.json transport/script/js/my-transport.js out.flux icon.png
  # icon.png is optional - omit the last argument for no icon

go run ./transport/script/cmd/scriptsign verify pub.key out.flux
```

`manifest.json` должен содержать хотя бы `{"name": "..."}`; `pack`
переписывает его поле `icon`, чтобы оно соответствовало тому файлу иконки
(если он есть), который вы реально передали — манифест пакета никогда не
может ссылаться на иконку, которой нет в архиве рядом с ним.

Добавьте `-store` к `pack`, чтобы оставить записи несжатыми вместо
стандартного deflate — формат поддерживает и то, и другое; при загрузке
пакета `.flux` не важно, что именно вы выбрали.

### Загрузка: `.flux` против `.js` — рантайм выбирает автоматически

Для данного имени транспорта загрузчик сначала пробует `<name>.flux`, при
отсутствии переходя на `<name>.js`. Вы не выбираете формат на уровне
CLI/конфига — просто кладёте собранный файл в директорию скриптов под
правильным именем.

## Общий код между скриптами: `scriptbundle`

Рантайм **никогда** не загружает JS-модуль с диска сам — единственный файл,
который он вообще выполняет, — тот один подписанный файл, который он
проверил. Если ваш транспорт хочет делить код с другим (решатель капчи,
клиент протокола, которым пользуются оба), напишите его как отдельный модуль
и встройте его на этапе сборки:

```js
// src/lib/mymodule.js
function doSomething() { /* ... */ }
module.exports = { doSomething: doSomething };
```

```js
// src/my-transport.js  (the SOURCE — not what gets signed)
var mymodule = require("./lib/mymodule.js");
mymodule.doSomething();
```

```bash
go run ./transport/script/cmd/scriptbundle \
  -entry src/my-transport.js -out my-transport.js
# NOW sign my-transport.js (the bundled output), not src/my-transport.js
go run ./transport/script/cmd/scriptsign sign priv.key my-transport.js
```

`scriptbundle` регэксп-сканирует вызовы `require("./relative/path.js")`
(только относительные — никакого разрешения пакетов, никакого
node_modules), рекурсивно встраивает каждый модуль в маленькую CommonJS-
обёртку-шим и выдаёт один плоский файл без рантайм-зависимости от
`require()`. Именно поэтому рантайму никогда не понадобился свой загрузчик
модулей: к моменту, когда вы что-либо подписываете, файл уже один, и его
подпись покрывает и *встроенный* код.

Держите свои авторские исходники с `require()` в директории вида `src/`,
отдельно от подписанного, загружаемого результата — собственное разделение
основного репозитория `transport/script/js/src/` против
`transport/script/js/*.js` — это образец для копирования. **Никогда не
редактируйте собранный результат вручную** — регенерируйте его из исходников
и подписывайте заново.

## Управление ключами на практике

- Одна пара ключей на домен доверия (например, «скрипты, которым доверяет
  этот exit») — самый простой вариант. Несколько ключей поддерживаются
  (`--script-pubkey` задаётся на уровне директории/вызова, а не глобально),
  но не тянитесь за этим, пока вам реально не понадобятся разные уровни
  доверия для разных транспортов.
- Ротация ключа означает переподпись каждого скрипта под ним и обновление
  `--script-pubkey` на каждом узле. Никакого протокола ротации ключей за
  этим не стоит — планируйте это как ручную, координируемую операцию.
- `.sig` (или `package.sig` у `.flux`) без соответствующего настроенного
  где-либо валидного публичного ключа — это просто неработающий файл:
  загрузчик отказывает явно (`script: <path>: signature verification
  failed`), он не пропускает проверку молча.
